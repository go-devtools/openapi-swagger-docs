## Three distinct checks

| Check | What it establishes |
| --- | --- |
| `openapi check --spec` | Document structure, supported semantic checks and offline references |
| `gin-swagger check --dir --output` | Generated bytes match current source and build inputs |
| `contracttest` with actual samples | The supplied sample agrees with the declared contract |

None of these alone proves that every execution path enforces a business rule. Test actual positive and negative requests against the existing application.

## Check a supplied document

From the core repository checkout:

```sh
GOWORK=off go run ./cmd/openapi check --spec ./testdata/golden/openapi32-full.json
```

`CheckWithOptions` accepts an explicit base URI, preloaded OpenAPI / JSON Schema resources and raw external examples. Checking never downloads references. Set bounded resources explicitly; a missing resource is a diagnostic rather than an invitation to fetch arbitrary URLs.

## Read diagnostics as evidence

Use diagnostic codes, severity, source, route, facts and fix fields. A successful check exits 0; document errors exit 1 and flag syntax errors exit 2. Installed CLI binaries expose the native exit codes; `go run` wraps program failures.

`Source.Kind` distinguishes derived, declared and unresolved provenance where present. `implementation: "not-proven"` in explanations means declarations have not been established as business enforcement.

## Current native boundaries

The checker supplements official schemas with tested Example, Discriminator and XML field checks, plus explicit boolean presence. It does not certify every discriminator composite inheritance context or XML name inference across use sites. Swagger UI's rendering capabilities are separate from document validity.

The independent validator accepts explicitly preloaded resources and checks actual samples with a separate engine. Read the source reference for options, budgets, recursion and streaming limitations.
